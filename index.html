STAGE 01 foundations

Containers & Docker

the unit everything else packages

A container bundles your app with everything it needs to run — runtime, libraries, config — into one image built from a Dockerfile. Unlike a VM it doesn't carry its own kernel; it shares the host's, which is why it starts in milliseconds instead of minutes.

  • Image — a read-only template built in layers, one per Dockerfile instruction.
  • Container — a running instance of an image. Ephemeral by default: anything not in a volume disappears on restart.
  • Registry — where images live (Docker Hub, Azure Container Registry). docker push/pull move them in and out.
  • Kubernetes doesn't run Docker directly — AKS nodes use containerd, the same OCI runtime Docker is built on. Your Dockerfile and images work unchanged.
Senior noteA small image ships faster and has a smaller attack surface. Multi-stage builds — compile in one stage, copy only the binary into a minimal final image — routinely cut image size by 10×.
Dockerfile + terminal
# build stage
FROM golang:1.22 AS build
WORKDIR /src
COPY . .
RUN go build -o /out/myapp

# final stage — nothing but the binary
FROM gcr.io/distroless/base
COPY --from=build /out/myapp /myapp
ENTRYPOINT ["/myapp"]

# build, tag, push to ACR
docker build -t myacr.azurecr.io/myapp:1.4.0 .
docker push myacr.azurecr.io/myapp:1.4.0

STAGE 02 foundations

Kubernetes basics

what problem it actually solves

Kubernetes keeps a declared number of containers running somewhere across a fleet of machines, restarts them when they die, and moves them when a machine fails — without anyone SSH-ing in to fix it by hand. You describe the desired state; controllers continuously drive the cluster toward it.

  • Declarative, not imperative — you say "3 replicas of this image," never "start container A on node B."
  • Reconciliation loop — controllers compare desired vs. actual state constantly and correct drift.
  • Everything is an object — Pods, Services, Deployments are records in the API, persisted in etcd.
  • AKS manages the parts that make this promise possible (the control plane); you manage what you ask it to run.
Senior noteThe mental shift that trips up people coming from VMs: you never "fix" a broken pod. You delete it and let the controller create a new, correct one. Debug the spec, not the individual pod.

STAGE 03 foundations

Architecture

control plane vs. data plane

Every cluster splits into two halves. The control plane makes decisions: the API server (front door for every request), the scheduler (picks which node a pod lands on), controller-manager (runs the reconciliation loops), and etcd (the cluster's database). The data plane is where workloads run: nodes, each with kubelet, kube-proxy, and a container runtime.

  • API server — the only thing anything talks to, including kubectl and the other control-plane pieces.
  • etcd — a distributed key-value store holding the entire cluster's state. Lose it, lose the cluster.
  • kubelet — the node agent that starts/stops containers per the API server's instructions.
  • On AKS the control plane is Azure-managed and mostly invisible; you only operate node pools.
Senior noteOn AKS the control plane is free and you never patch it — that's the actual value of a managed service. You're responsible for the data plane: node OS patching (largely automated), sizing, and what you schedule onto it.
terminal
kubectl cluster-info
kubectl get nodes -o wide
kubectl get --raw /healthz       # is the API server up?
kubectl get pods -n kube-system  # control-plane helpers

STAGE 04 foundations

kubectl

the only tool you need for 90% of your day

kubectl talks to the API server over HTTPS and turns your commands into API requests. Almost everything you do — read, create, edit, delete, debug — goes through it, so fluency here compounds fast.

  • get / describe / logs / exec — your core debugging loop for reading state.
  • apply -f — declarative: hands a YAML file to the API server and lets it diff against current state.
  • create / delete — imperative, fine for scratch work, not for anything you want reproducible.
  • -o yaml / --dry-run=client -o yaml — turn any live object, or any command, into starter YAML.
Senior notekubectl explain <resource>.<field> pulls docs straight from the cluster's own OpenAPI schema — faster than the web docs, and it never drifts from the version you're actually running.
terminal
kubectl get pods -n myapp-prod -o wide
kubectl describe pod myapp-7d9f -n myapp-prod
kubectl logs -f myapp-7d9f -n myapp-prod
kubectl exec -it myapp-7d9f -n myapp-prod -- sh
kubectl explain deployment.spec.strategy
kubectl apply -f deployment.yaml --dry-run=client -o yaml
STAGE 05 core objects

Pods

the smallest thing you actually deploy

A pod is one or more containers that share a network namespace (they talk over localhost) and can share storage volumes. It's the smallest unit Kubernetes schedules — and on its own, it's fragile: a bare pod that dies stays dead.

  • Usually one container per pod; multi-container pods are for tightly coupled helpers (sidecars), not general composition.
  • Pods are mortal — nodes fail, pods get evicted, IPs churn. Nothing in production should be a bare pod.
  • Init containers run to completion before the main container starts — good for "wait for the DB" setup.
  • kubectl run is for scratch debugging only, never how you ship anything real.
Senior noteIf you find yourself kubectl apply-ing a bare Pod for anything but a one-off debug container, stop — you want a Deployment. Bare pods don't get rescheduled if the node dies.
pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-debug
spec:
  initContainers:
  - name: wait-for-db
    image: busybox
    command: [sh, -c, until nc -z db 5432; do sleep 1; done]
  containers:
  - name: myapp
    image: myacr.azurecr.io/myapp:1.4.0
    ports: [{ containerPort: 8080 }]

STAGE 06 core objects

YAML

the syntax, not the concept

Every Kubernetes object — from a Pod to a ClusterRoleBinding — follows the same shape: apiVersion, kind, metadata, spec. Learn that shape once and you can read any manifest, even for resources you've never used.

  • apiVersion — which API group/version defines this kind (v1, apps/v1, networking.k8s.io/v1...).
  • kind — the resource type: Pod, Deployment, Service...
  • metadata — name, namespace, labels, annotations. Identity and tags, not behavior.
  • spec — the desired state you declare; status is filled in by the cluster, never written by hand.
Senior noteIndentation is meaningful and it's spaces only. A stray tab is the single most common reason kubectl apply throws a parse error — run everything through --dry-run=client before you commit it.
anatomy.yaml
apiVersion: apps/v1        # which API defines "kind" below
kind: Deployment           # the resource type
metadata:                 # identity: name, namespace, labels
  name: myapp
  namespace: myapp-prod
  labels: { app: myapp }
spec:                     # desired state — you write this
  replicas: 3
# status:                    ← cluster-managed, never hand-written
STAGE 07 core objects

Deployments & ReplicaSets

how pods actually stay alive

A Deployment doesn't manage pods directly — it manages a ReplicaSet, which manages the pods. You'll almost never touch a ReplicaSet by hand; it exists so the Deployment has something to swap out during a rolling update.

  • Deployment — declares desired replica count and pod template; owns the rollout strategy.
  • ReplicaSet — keeps N pods matching a label selector running at all times.
  • A rolling update creates a new ReplicaSet and scales it up while scaling the old one down — that's zero-downtime deploys.
  • kubectl rollout undo is instant because the previous ReplicaSet is still there, just scaled to zero.
Senior notekubectl get replicasets after a few deploys shows old, scaled-to-zero ReplicaSets sitting around — that's normal, it's what makes rollback instant. revisionHistoryLimit controls how many it keeps.
deployment.yaml + terminal
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  namespace: myapp-prod
spec:
  replicas: 3
  revisionHistoryLimit: 5
  selector: { matchLabels: { app: myapp } }
  template:
    metadata: { labels: { app: myapp } }
    spec:
      containers:
      - name: myapp
        image: myacr.azurecr.io/myapp:1.5.0

kubectl rollout status deploy/myapp -n myapp-prod
kubectl rollout undo deploy/myapp -n myapp-prod

STAGE 08 core objects

Services

a stable address for a shifting set of pods

Pods die and get replaced with new IPs constantly. A Service gives them one stable address regardless of which pods are behind it at any moment — it's a label selector plus a virtual IP, not a process.

  • ClusterIP (default) — reachable only inside the cluster. Most services should be this.
  • NodePort — opens a port on every node. Rarely used directly.
  • LoadBalancer — on AKS, provisions an actual Azure Standard Load Balancer with a public (or, via annotation, private) IP.

This is Layer 4: it balances TCP/UDP connections across nodes with zero awareness of HTTP paths, hostnames, or headers. For that, you need Ingress — stage 15.

Senior noteEvery type: LoadBalancer Service provisions its own Azure Load Balancer and its own public IP. Fine for one or two entry points; expensive and hard to manage once you have ten services to expose. That's exactly the problem Ingress solves.
service.yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp
  namespace: myapp-prod
  annotations:
    # drop this line for a public IP instead
    service.beta.kubernetes.io/azure-load-balancer-internal: "true"
spec:
  type: LoadBalancer
  selector: { app: myapp }
  ports:
  - { port: 443, targetPort: 8080 }

STAGE 09 core objects

Labels & selectors

how Kubernetes finds things

Labels are arbitrary key-value tags on objects. Selectors are queries against those tags. Nearly every relationship in Kubernetes — which pods a Deployment owns, which pods a Service routes to — is a selector matching labels, not a direct pointer.

  • A Deployment's selector.matchLabels must match its pod template's labels — mismatch it and the Deployment can't find its own pods.
  • Services find pods by selector, not by name — rename or replace a pod and nothing breaks.
  • Annotations look similar but aren't selectable. Use labels for anything you query on; annotations for metadata tooling reads (build SHA, owner).
  • kubectl get pods -l app=myapp,tier=backend — selector syntax works from the CLI too.
Senior noteA classic self-inflicted outage: someone edits a Deployment's label selector "to tidy it up." Selectors are immutable on Deployments for exactly this reason — you have to recreate the object, not patch it.
terminal
metadata:
  labels: { app: myapp, tier: backend, env: prod }

# find pods by label from the CLI
kubectl get pods -l app=myapp,tier=backend
kubectl get pods -l 'env in (prod,staging)'
selector matches labels, not names
selector: app=myapp

STAGE 10 core objects

Namespaces

a logical wall, not a security boundary

A namespace partitions one cluster into separate zones for names, quotas, and permissions. It does not isolate at the kernel or network level by default — a pod in dev can still reach a pod in prod unless a NetworkPolicy says otherwise (stage 21).

Three ship built in: default, kube-system (cluster internals — leave it alone), and kube-public. Everything you create should get its own.

  • One namespace per environment (or per team, or per app) — pick a convention and stick to it.
  • ResourceQuota caps total CPU/memory a namespace can consume.
  • RoleBinding scopes who can do what, per namespace (stage 20).
Senior noteA namespace stops your team from starving another team's CPU quota. It does nothing against a container escape or a misconfigured Service reaching across namespaces — that's a different layer entirely.
kubectl create namespaceResourceQuotaLimitRangeRoleBinding
namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: myapp-prod
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: myapp-quota
  namespace: myapp-prod
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi

STAGE 11 core objects

ConfigMaps & Secrets

configuration that lives outside the image

Baking config into an image means rebuilding it for every environment. ConfigMaps and Secrets let the same image run in dev, staging, and prod with different config injected at deploy time — as env vars or mounted files.

  • ConfigMap — non-sensitive config: feature flags, URLs, log levels.
  • Secret — same shape, but base64-encoded (not encrypted by default) and handled specially by RBAC. Base64 is encoding, not security.
  • Mount as env vars for values read once at startup; mount as a volume for values that should update without a restart.
  • On AKS, prefer Azure Key Vault + the Secrets Store CSI Driver (backed by the Workload Identity from stage 20) over native Secrets for anything genuinely sensitive.
Senior noteA Secret changing doesn't restart pods that mounted it as an env var — they keep the stale value until the next rollout. Mount as a volume if it needs to update live, or trigger a rollout on change with a checksum annotation.
config.yaml
apiVersion: v1
kind: ConfigMap
metadata: { name: myapp-config, namespace: myapp-prod }
data:
  LOG_LEVEL: info
---
apiVersion: v1
kind: Secret
metadata: { name: myapp-secret, namespace: myapp-prod }
stringData:
  API_KEY: change-me
---
# in the pod spec:
envFrom:
- configMapRef: { name: myapp-config }
- secretRef: { name: myapp-secret }
STAGE 12 reliability & state

Health probes

how Kubernetes knows a pod actually works

A pod with status "Running" isn't the same as a pod that's ready to serve traffic. Probes are how you tell Kubernetes the difference.

  • livenessProbe — fails repeatedly and Kubernetes kills and restarts the container. For "it's stuck," not "it's slow."
  • readinessProbe — fails and the pod is pulled out of Service endpoints, but not restarted. For "not ready yet."
  • startupProbe — covers slow-starting apps; liveness/readiness don't start checking until this passes.
  • HTTP, TCP, or exec — pick whichever actually reflects health; an exec probe that always returns 0 tells you nothing.
Senior noteThe single most common self-inflicted outage: a liveness probe with too aggressive a timeout on a service that occasionally runs a slow query. It kills healthy pods in a loop under load — exactly when you can least afford it. When in doubt, make liveness lenient and readiness strict.
probes.yaml
containers:
- name: myapp
  startupProbe:
    httpGet: { path: /healthz, port: 8080 }
    failureThreshold: 30
    periodSeconds: 2
  readinessProbe:
    httpGet: { path: /ready, port: 8080 }
    periodSeconds: 5
  livenessProbe:
    httpGet: { path: /healthz, port: 8080 }
    periodSeconds: 15
    timeoutSeconds: 5
    failureThreshold: 3
what each probe governs

STAGE 13 reliability & state

Volumes, PV, PVC, StorageClass

pods are ephemeral by design

Anything a container writes to its own filesystem vanishes on restart. The chain that survives it: a StorageClass (how to provision), a PersistentVolumeClaim (a pod's request for storage), and the PersistentVolume the cluster binds to it.

  • AKS ships three CSI drivers pre-installed: Azure Disk (block, ReadWriteOnce — one pod at a time, good for a database), Azure Files (SMB/NFS, ReadWriteMany — shared config), Azure Blob (object storage, large unstructured data).
  • A PVC is a request, not a guarantee — it stays Pending until something can satisfy it.
  • Deleting a PVC's pod doesn't delete the PVC; deleting the PVC's reclaimPolicy decides whether the underlying disk is deleted or retained.
Senior noteDisk-backed volumes are zone-bound. If your node pool spans zones but the disk was provisioned in only one, a rescheduled pod can get stuck Pending waiting for a node in the disk's zone. Match the StorageClass's allowedTopologies to your node pool's zones.
storage.yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: managed-premium-zrs
provisioner: disk.csi.azure.com
parameters:
  skuName: PremiumV2_ZRS
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: myapp-data
  namespace: myapp-prod
spec:
  storageClassName: managed-premium-zrs
  accessModes: [ReadWriteOnce]
  resources:
    requests: { storage: 20Gi }

STAGE 14 reliability & state

StatefulSets

when identity and order matter

A Deployment's pods are interchangeable — replica #2 dying and coming back with a new name and a new disk is fine. A StatefulSet exists for workloads where that's not fine: databases, brokers, anything where "which one is this" and "in what order did it start" matters.

  • Stable, predictable pod names — myapp-0, myapp-1, myapp-2, not random suffixes.
  • Each replica gets its own PVC via volumeClaimTemplates, and keeps the same one across restarts.
  • Ordered, sequential start/stop by default (0, then 1, then 2) — matters for clustered databases with a defined join order.
  • Needs a headless Service (clusterIP: None) so each pod gets its own stable DNS name.
Senior noteMost teams reach for a StatefulSet before they need one. If the data belongs in a managed Azure service (Azure Database for PostgreSQL, Cosmos DB), running it yourself on a StatefulSet is usually more operational burden than benefit — good to know it exists, better to avoid needing it.
statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: myapp-db, namespace: myapp-prod }
spec:
  serviceName: myapp-db     # headless Service
  replicas: 3
  selector: { matchLabels: { app: myapp-db } }
  template:
    metadata: { labels: { app: myapp-db } }
    spec: { containers: [{ name: db, image: postgres:16 }] }
  volumeClaimTemplates:
  - metadata: { name: data }
    spec:
      accessModes: [ReadWriteOnce]
      resources: { requests: { storage: 50Gi } }
stable identity, own disk each

STAGE 15 traffic

Ingress

one IP, routed by hostname and path

Ingress operates at Layer 7: one public IP in front of the cluster, routing by hostname and URL path, terminating TLS in a single place instead of per-service.

Two common controllers on AKS:

  • NGINX Ingress Controller — open source, installed via Helm, the default choice for most teams.
  • Application Gateway Ingress Controller (AGIC) — routes through a real Azure Application Gateway, brings a managed WAF.

An Ingress resource is just routing rules; something still has to run the controller that reads them and configures a real proxy.

Senior noteThe Ingress API is stable but frozen — it can't cleanly express weighted traffic splitting or cross-namespace routing. That's what the newer Gateway API (Azure's managed flavor: Application Gateway for Containers) exists to fix. Worth knowing it exists; don't fight Ingress into doing something it wasn't built for.
ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp
  namespace: myapp-prod
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt
spec:
  ingressClassName: nginx
  tls:
  - { hosts: [app.example.com], secretName: myapp-tls }
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service: { name: myapp, port: { number: 443 } }

STAGE 16 traffic

Networking basics

the rules every pod already gets for free

Kubernetes networking has one foundational rule: every pod gets its own IP, and every pod can reach every other pod's IP directly, cluster-wide, no NAT — regardless of which node they're on. Services, Ingress, and policies are all built on top of that flat model.

  • CNI plugin — Azure CNI (pods get real, VNet-routable IPs) or kubenet (pods get an overlay IP, NAT'd at the node). Decided at cluster creation, hard to change later.
  • kube-proxy — runs on every node, programs the rules that make a Service's virtual IP actually route to real pod IPs.
  • CoreDNS — cluster-internal DNS. Every Service gets a name: myapp.myapp-prod.svc.cluster.local.
  • DNS resolution inside a pod follows its namespace's search domains — myapp resolves in the same namespace, myapp.other-ns reaches across.
Senior note"Pod can't reach pod" is almost never actually a Kubernetes networking bug — it's usually an NSG rule at the Azure VNet layer, or a NetworkPolicy (stage 21) doing exactly what it was configured to do. Check those two before you suspect the CNI.
terminal
kubectl get svc myapp -n myapp-prod
kubectl get endpoints myapp -n myapp-prod
kubectl run dnsutils --rm -it --image=gcr.io/kubernetes-e2e-test-images/dnsutils -- \
  nslookup myapp.myapp-prod.svc.cluster.local

STAGE 17 scheduling & workloads

Jobs, CronJobs, DaemonSets

workloads that aren't "always-on services"

Not everything is a long-running web server. Three more controllers cover the rest of the shape space.

  • Job — runs a pod to completion, retries on failure, then stops. Migrations, one-off batch tasks.
  • CronJob — a Job on a schedule, cron syntax. Nightly reports, cleanup tasks.
  • DaemonSet — runs exactly one pod per node, automatically added when a new node joins. Log shippers, node-level monitoring agents.
  • completions / parallelism on a Job control how many pods run in total, and how many run at once.
Senior noteA CronJob's concurrencyPolicy defaults to Allow — a slow run and its next scheduled run can overlap and execute concurrently. Set it to Forbid for anything that isn't safe to run twice at once.
cronjob.yaml
apiVersion: batch/v1
kind: CronJob
metadata: { name: nightly-report, namespace: myapp-prod }
spec:
  schedule: "0 2 * * *"
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      template:
        spec:
          containers: [{ name: report, image: myacr.azurecr.io/report-job:1.0 }]
          restartPolicy: OnFailure
STAGE 18 scheduling & workloads

Resource requests & limits

what the scheduler and the kernel actually enforce

Requests are what the scheduler uses to decide which node has room for a pod. Limits are what the kernel enforces once it's running. Two different questions — mixing them up causes two different classes of incident.

  • No request set → the pod is BestEffort, first to be evicted when a node runs low on resources.
  • CPU limit → throttled, not killed. The container keeps running but slows down, often invisibly — it shows up as latency, not an error.
  • Memory limit → OOM-killed, not throttled. Hit it and the container is terminated and restarted immediately.
  • Requests should reflect steady-state usage; limits should reflect the worst case you're willing to tolerate — set both from real metrics, not guesses.
Senior noteSet requests too high across a namespace and the cluster autoscaler adds nodes you don't need, purely because the scheduler thinks there's no room. Check actual usage with kubectl top pods before tuning either number.
terminal + resources.yaml
resources:
  requests: { cpu: 250m, memory: 256Mi }
  limits:   { memory: 512Mi }

kubectl top pods -n myapp-prod
kubectl top nodes
two different failure modes
CPU limit hitthrottled → slow, no crash
memory limit hitOOMKilled → restart
STAGE 19 scheduling & workloads

Taints, tolerations, affinity

steering which pods land where

By default the scheduler treats all matching nodes as interchangeable. Three mechanisms narrow that down — one from the node's side, two from the pod's.

  • Taint (on a node) — repels pods unless they carry a matching toleration. "Nothing schedules here unless it explicitly says it's OK."
  • Toleration (on a pod) — the pod's half of the handshake: "I'm fine running on that tainted node."
  • Node affinity — "schedule me only on nodes with label X" (or preferably, softly).
  • Pod anti-affinity — "schedule me away from other pods matching this label" — how you spread replicas across nodes or zones so one failure doesn't take out the whole Deployment.
Senior noteAKS's system node pool ships tainted CriticalAddonsOnly=true:NoSchedule in many setups specifically to keep app workloads off it — the pattern from stage 03, now with the actual mechanism behind it.
terminal + affinity.yaml
kubectl taint nodes aks-system-001 CriticalAddonsOnly=true:NoSchedule

# the pod's side:
tolerations:
- { key: CriticalAddonsOnly, operator: Equal, value: "true", effect: NoSchedule }

affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - topologyKey: kubernetes.io/hostname
      labelSelector: { matchLabels: { app: myapp } }
STAGE 20 security

RBAC & ServiceAccounts

who's allowed to do what, and who is the pod

RBAC governs humans and automation calling the Kubernetes API; a ServiceAccount is a pod's identity when it calls that same API. Same authorization model, just a different caller.

  • Role / ClusterRole — a set of permitted verbs (get, list, watch, create...) on a set of resources, namespaced or cluster-wide.
  • RoleBinding / ClusterRoleBinding — grants a Role to a user, group, or ServiceAccount.
  • Every pod runs as a ServiceAccount (default, if you don't specify one) — and that default account should almost always have zero permissions.
  • On AKS, Azure AD Workload Identity federates a ServiceAccount to a real Azure identity — authentication to Azure, layered on top of (not instead of) this Kubernetes-native authorization model.
Senior noteThe default ServiceAccount in every namespace can, by default, do almost nothing — good. The mistake is granting it broad permissions "to unblock something quickly" and forgetting every unspecified pod in that namespace inherits it.
rbac.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: pod-reader, namespace: myapp-prod }
rules:
- { apiGroups: [""], resources: [pods], verbs: [get, list, watch] }
---

STAGE 21 security

Network Policies & security basics

the flat network isn't the final answer

Stage 16 established that every pod can reach every other pod by default. A NetworkPolicy takes that back — an allow-list firewall scoped to pod selectors, enforced by the CNI plugin, not the API server itself.

  • Default-deny — a NetworkPolicy selecting a pod with no rules blocks all traffic to it; you then add explicit allow rules.
  • Ingress rules control what can call in; egress rules control what the pod itself can call out to.
  • Requires a CNI that actually enforces NetworkPolicy — Azure CNI does with Azure Network Policy or Calico enabled. Check this isn't silently a no-op on your cluster.
  • Beyond NetworkPolicy: Pod Security Standards (no privileged containers, no host network) and image scanning round out baseline security.
Senior noteApplying your first default-deny NetworkPolicy in a namespace with existing traffic is a great way to cause an outage that looks like nothing changed on your end. Map every legitimate path first and ship the allow rules alongside the deny, not after.
networkpolicy.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: myapp-allow, namespace: myapp-prod }
spec:
  podSelector: { matchLabels: { app: myapp } }
  policyTypes: [Ingress]
  ingress:
  - from:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: myapp-prod } }
    ports: [{ port: 8080 }]

STAGE 22 operating a cluster

Helm

package manager for Kubernetes manifests

Once you're managing more than a handful of YAML files per app, templating and versioning them by hand gets old fast. Helm packages manifests into a chart with values you override per environment, and tracks what's installed as a release you can upgrade or roll back as one unit.

  • Chart — a directory of templated YAML plus a values.yaml of defaults.
  • Release — one installed instance of a chart in a cluster/namespace, with its own override values.
  • helm upgrade --install is idempotent — safe on first install and every deploy after.
  • Most infra you'd otherwise hand-write (NGINX ingress controller, cert-manager, Prometheus) ships as an official chart — check before you write it yourself.
Senior noteRun helm diff (plugin) or --dry-run before every upgrade in prod. A chart's default values changing between versions is a common source of "I only bumped the version number" surprises.
terminal
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm upgrade --install ingress-nginx ingress-nginx/ingress-nginx \
  --namespace ingress-nginx --create-namespace \
  --set controller.replicaCount=2

helm list -n ingress-nginx
helm rollback ingress-nginx 1 -n ingress-nginx
STAGE 23 operating a cluster

Monitoring & logging

knowing what's actually happening

kubectl logs and describe are your first line of defense, but they don't scale past one incident on one pod. Real operations needs metrics and logs aggregated somewhere that survives the pod that produced them.

  • Metrics — Prometheus (often the kube-prometheus-stack chart) scrapes cluster and app metrics; on AKS, Azure Monitor managed Prometheus is the managed alternative.
  • Dashboards — Grafana, usually paired with Prometheus.
  • Logs — pods should log stdout/stderr only; a node-level agent (Fluent Bit, Azure Monitor Container Insights) ships it off-node before the pod disappears.
  • metrics-server (already running in your system pool since stage 03) powers kubectl top and HPA — not a full monitoring stack, just enough for those two.
Senior noteIf your only copy of a pod's logs is kubectl logs, you have zero logs the moment that pod is evicted. Anything you'd need for a postmortem has to leave the node before that happens.

STAGE 24 operating a cluster

Autoscaling

three different things scale, for three different reasons

"Autoscaling" in Kubernetes is actually three separate mechanisms, each solving a different bottleneck.

  • HorizontalPodAutoscaler (HPA) — adds/removes pod replicas based on CPU/memory or custom metrics. Solves "not enough pods for the traffic."
  • VerticalPodAutoscaler (VPA) — adjusts a pod's requests/limits over time based on observed usage. Rarely run alongside HPA on the same metric.
  • Cluster Autoscaler — adds/removes nodes when pods are unschedulable or nodes sit idle. Solves "not enough room in the cluster."
  • They stack: HPA decides you need more pods → scheduler can't place them → Cluster Autoscaler adds a node.
Senior noteHPA needs requests set (stage 18) to compute a percentage at all — no requests, no scaling decision, full stop.
hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: myapp, namespace: myapp-prod }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: myapp }
  minReplicas: 3
  maxReplicas: 10
  metrics:
  - type: Resource
    resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }

STAGE 25 operating a cluster

Troubleshooting

a repeatable order of operations, not guessing

Almost every "something's broken" starts the same way. Work outward from the pod before you start suspecting the network or the cluster.

  • kubectl get pods — the status tells you where to look: Pending (can't schedule), CrashLoopBackOff (starts then dies), ImagePullBackOff (can't fetch the image).
  • kubectl describe pod — the Events section at the bottom almost always holds the real reason.
  • kubectl logs (add --previous if it already restarted) — what the app itself said before it died.
  • kubectl get events --sort-by=.lastTimestamp -n <ns> — cluster-wide events when it's not obviously one pod's fault.
Senior notePending almost always means the scheduler can't find a fit — check node resources, taints/tolerations, and PVC binding before suspecting the app. CrashLoopBackOff almost always means the app itself is exiting — that's a logs problem, not a Kubernetes problem.

STAGE 26 shipping & mastery

CI/CD & GitOps

how changes actually get to the cluster

Manually kubectl apply-ing from a laptop doesn't scale past a demo. Two patterns replace it, and most real setups combine them.

  • CI pipeline (GitHub Actions, Azure Pipelines) — builds the image, runs tests, pushes to ACR on every commit.
  • Push-based deploy — the pipeline itself runs kubectl apply or helm upgrade against the cluster.
  • GitOps (Flux, Argo CD) — pull-based instead: an operator inside the cluster watches a Git repo and reconciles the cluster to match it. Nothing outside the cluster gets direct push access.
  • Git becomes the single source of truth — a manual kubectl apply not reflected in Git is now drift the GitOps operator will quietly revert.
Senior noteGitOps' biggest real benefit isn't automation, it's the audit trail — every change to the cluster is a Git commit with an author and a diff, which turns "what changed right before this broke" from an afternoon into a five-second question.
.github/workflows/deploy.yml
jobs:
  build:
    steps:
      - run: docker build -t $ACR/myapp:${{ github.sha }} .
      - run: docker push $ACR/myapp:${{ github.sha }}
      - run: |
          # push-based:
          kubectl set image deploy/myapp myapp=$ACR/myapp:${{ github.sha }}
          # GitOps instead: commit the new tag, let Flux/Argo CD apply it

CKA/CKS/CKAD prep

Three CNCF certifications, same format: open-book, terminal-only, timed hands-on labs — no multiple choice, just kubectl and a clock.

  • CKAD (Application Developer) — closest to stages 1–19 above: pods, deployments, config, probes, storage, from the app author's side.
