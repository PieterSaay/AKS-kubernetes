STAGE 00 foundation

Resource group & virtual network

before any Kubernetes exists

Every Azure resource you create — the cluster, the storage account, the public IP — has to live inside a resource group: a folder for billing, permissions, and cleanup. Delete the group, delete the whole environment.

AKS nodes are Azure VMs, and VMs need addresses, so the cluster needs a virtual network (VNet) and a subnet to launch into. The networking mode you choose here — kubenet (nodes get real IPs, pods get an overlay) or Azure CNI (pods get real, routable VNet IPs) — is a decision you make once. Changing it later usually means rebuilding the cluster.

  • Resource group — the container everything below lives in.
  • VNet + subnet — the private network the cluster's nodes attach to.
  • CNI choice — determines how many IP addresses your subnet needs to reserve.
Senior noteWith Azure CNI, every pod eats a real IP from the subnet, not just every node. Undersize the subnet and you'll hit a wall at 40% cluster capacity, not 100%. Size for pods, not nodes.
terminal
# resource group — everything else lives here
az group create \
  --name rg-myapp-prod \
  --location westeurope

# network the nodes will launch into
az network vnet create \
  --resource-group rg-myapp-prod \
  --name vnet-myapp \
  --address-prefix 10.0.0.0/8 \
  --subnet-name snet-aks \
  --subnet-prefix 10.240.0.0/16

STAGE 01 compute

The cluster & its nodes

control plane + node pools

An AKS cluster is really two separate things billed differently. The control plane — API server, scheduler, etcd — is managed and (mostly) free; you never see or patch it. The node pools are Azure VM scale sets you pay for, patch, and size.

A node is one VM running kubelet (talks to the control plane), kube-proxy (networking rules), and a container runtime (containerd). Every AKS cluster needs a system node pool for cluster-critical pods — CoreDNS, metrics-server — and should get at least one user node pool for your actual application.

  • System pool — keeps the cluster alive. Keep app workloads off it.
  • User pool(s) — where your Deployments actually schedule; scale/size per workload.
  • Cluster autoscaler — adds/removes nodes based on unschedulable pods.
  • Availability zones — spread nodes across zones so one datacenter failure isn't an outage.
Senior noteA noisy pod on the system pool can starve CoreDNS of CPU and take down DNS resolution for the entire cluster. Taint the system pool (CriticalAddonsOnly) and give your app its own pool — it's cheap insurance.
terminal
az aks create \
  --resource-group rg-myapp-prod \
  --name aks-myapp-prod \
  --vnet-subnet-id <subnet-id> \
  --network-plugin azure \
  --node-count 3 \
  --node-vm-size Standard_D4s_v5 \
  --zones 1 2 3 \
  --enable-cluster-autoscaler \
  --min-count 3 --max-count 6

# add a dedicated pool for the app
az aks nodepool add \
  --cluster-name aks-myapp-prod \
  --resource-group rg-myapp-prod \
  --name userpool \
  --node-vm-size Standard_D4s_v5 \
  --mode User

STAGE 02 isolation

Namespaces

a logical wall, not a security boundary

A namespace partitions one cluster into separate zones for names, quotas, and permissions. It does not isolate at the kernel or network level by default — a pod in dev can still reach a pod in prod unless a NetworkPolicy says otherwise.

Three ship built in: default, kube-system (cluster internals — leave it alone), and kube-public. Everything you create should get its own.

  • One namespace per environment (or per team, or per app) — pick a convention and stick to it.
  • ResourceQuota caps total CPU/memory a namespace can consume.
  • RoleBinding scopes who can do what, per namespace.
Senior noteA namespace stops your team from starving another team's CPU quota. It does nothing against a container escape or a misconfigured Service reaching across namespaces — that's NetworkPolicy and pod security, a different layer entirely.
kubectl create namespaceResourceQuotaLimitRangeRoleBinding
namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: myapp-prod
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: myapp-quota
  namespace: myapp-prod
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi

STAGE 03 workload

Pods & workloads

the smallest thing you actually deploy

A pod is one or more containers that share a network namespace (they talk over localhost) and can share storage volumes. It's the smallest unit Kubernetes schedules — but you will almost never create a bare Pod.

Instead you wrap pods in a controller that matches the shape of your workload:

  • Deployment — stateless, replaceable, rolling updates. Your default choice.
  • StatefulSet — stable identity and storage per replica. Databases, brokers.
  • DaemonSet — exactly one pod per node. Log shippers, node agents.
  • Job / CronJob — run to completion, once or on a schedule.

Resource requests tell the scheduler how much CPU/memory a pod needs to be placed on a node — and drive the cluster autoscaler. Limits cap what it can use. Skip requests and your pod is "BestEffort" — first in line to be evicted when a node runs low.

Senior noteSet memory limits close to real usage — an OOM-killed pod restarts cleanly. Be cautious with CPU limits: they cause invisible throttling under load that doesn't show up as an error, just as latency. Measure before you cap.
deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  namespace: myapp-prod
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: myapp
        image: myacr.azurecr.io/myapp:1.4.0
        resources:
          requests: { cpu: 250m, memory: 256Mi }
          limits:   { memory: 512Mi }
        readinessProbe:
          httpGet: { path: /healthz, port: 8080 }

STAGE 04 identity

Managed identity

no secrets baked into config maps, ever

Two identities operate at two different layers — don't conflate them.

The cluster's own managed identity is what AKS itself uses to talk to Azure: attaching disks, creating a Load Balancer, pulling images from ACR. You barely think about it; Azure sets it up when the cluster is created.

Azure AD Workload Identity is the one you'll use constantly: it lets a specific pod — via its Kubernetes ServiceAccount — exchange a token for a real Azure AD identity, and from there call Key Vault, Storage, or SQL with no client secret anywhere in your YAML.

  • Create a user-assigned managed identity in Azure.
  • Federate it to a Kubernetes ServiceAccount via OIDC — no secret changes hands.
  • Grant that identity a role (e.g. Key Vault Secrets User) on the target resource.
  • Your app's SDK picks up the token automatically — nothing app-side to manage.
Senior noteIf you inherit a cluster still using AAD Pod Identity, flag it — it's deprecated. Workload Identity (OIDC federation) has been the supported path since AKS 1.24 and is what Microsoft's docs assume now.
terminal + service-account.yaml
az identity create -g rg-myapp-prod -n id-myapp

az identity federated-credential create \
  --name myapp-fed \
  --identity-name id-myapp \
  --resource-group rg-myapp-prod \
  --issuer <aks-oidc-issuer-url> \
  --subject system:serviceaccount:myapp-prod:myapp-sa

# the pod-facing side
apiVersion: v1
kind: ServiceAccount
metadata:
  name: myapp-sa
  namespace: myapp-prod
  annotations:
    azure.workload.identity/client-id: <identity-client-id>

STAGE 05 state

Azure storage

pods are ephemeral by design

Anything a container writes to its own filesystem vanishes on restart. For anything that needs to survive, AKS ships three CSI drivers pre-installed, each suited to a different access pattern:

  • Azure Disk — block storage, ReadWriteOnce (one pod at a time). The default for a database's data directory.
  • Azure Files — an SMB/NFS share, ReadWriteMany (many pods at once). Shared config, uploads.
  • Azure Blob — object storage, mounted via CSI or called directly from app code. Large unstructured data, backups.

The flow is always: StorageClass (how to provision) → PersistentVolumeClaim (a pod's request for storage) → Pod (mounts the claim as a volume).

Senior noteDisk-backed volumes are zone-bound. If your node pool spans zones but the disk was provisioned in only one, a rescheduled pod can get stuck Pending waiting for a node in the disk's zone. Match your StorageClass's allowedTopologies to your node pool's zones.
storage.yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: managed-premium-zrs
provisioner: disk.csi.azure.com
parameters:
  skuName: PremiumV2_ZRS
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: myapp-data
  namespace: myapp-prod
spec:
  storageClassName: managed-premium-zrs
  accessModes: [ReadWriteOnce]
  resources:
    requests: { storage: 20Gi }

STAGE 06 traffic in · layer 4

Services & load balancing

a stable address for a shifting set of pods

Pods die and get replaced with new IPs constantly. A Service gives them one stable address regardless of which pods are behind it at any moment.

  • ClusterIP (default) — reachable only inside the cluster. Most services should be this.
  • NodePort — opens a port on every node. Rarely used directly.
  • LoadBalancer — provisions an actual Azure Standard Load Balancer with a public (or, via annotation, private) IP.

This is Layer 4: it balances TCP/UDP connections across nodes with zero awareness of HTTP paths, hostnames, or headers. For that, you need Ingress or Gateway API — next.

Senior noteEvery type: LoadBalancer Service provisions its own Azure Load Balancer and its own public IP. Fine for one or two entry points; expensive and hard to manage once you have ten services to expose. That's exactly the problem Ingress solves.
service.yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp
  namespace: myapp-prod
  annotations:
    # drop this line for a public IP instead
    service.beta.kubernetes.io/azure-load-balancer-internal: "true"
spec:
  type: LoadBalancer
  selector: { app: myapp }
  ports:
  - { port: 443, targetPort: 8080 }

STAGE 07 traffic in · layer 7

Ingress

one IP, routed by hostname and path

Ingress operates at Layer 7: one public IP in front of the cluster, routing by hostname and URL path, terminating TLS in a single place instead of per-service.

Two common controllers on AKS:

  • NGINX Ingress Controller — open source, installed via Helm, the default choice for most teams.
  • Application Gateway Ingress Controller (AGIC) — routes through a real Azure Application Gateway, brings a managed WAF.

An Ingress resource is just routing rules; something still has to run the controller that reads them and configures a real proxy.

Senior noteThe Ingress API is stable but frozen — it can't cleanly express weighted traffic splitting or cross-namespace routing. That gap is exactly why Gateway API exists. Don't fight Ingress into doing something it wasn't built for.
ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp
  namespace: myapp-prod
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt
spec:
  ingressClassName: nginx
  tls:
  - { hosts: [app.example.com], secretName: myapp-tls }
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service: { name: myapp, port: { number: 443 } }

STAGE 08 traffic in · next gen

Gateway API

Ingress, split by who owns what

Gateway API is Ingress's successor, and it fixes the ownership problem by splitting one YAML file into role-shaped resources:

  • GatewayClass — a class of gateway implementation. Owned by whoever manages the cluster.
  • Gateway — an actual listener and IP. Owned by the platform team.
  • HTTPRoute — routing rules for one app. Owned by the app team, and can live in the app's own namespace.

Azure's managed implementation is Application Gateway for Containers (AGC). The practical win: app teams ship their own routing changes without ever touching the shared Gateway resource or filing a ticket with platform.

Senior noteDon't migrate a working Ingress setup just to be on the newer thing. Reach for Gateway API when you actually need what it offers — weighted/canary routing, or routes that app teams own directly in their own namespace.
gateway.yaml + httproute.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shared-gw
  namespace: platform
spec:
  gatewayClassName: azure-alb-external
  listeners:
  - { name: https, port: 443, protocol: HTTPS }
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: myapp-route
  namespace: myapp-prod
spec:
  parentRefs: [{ name: shared-gw, namespace: platform }]
  hostnames: [app.example.com]
  rules:
  - backendRefs: [{ name: myapp, port: 443 }]
